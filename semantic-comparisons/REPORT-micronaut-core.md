# Task graph and task input/output differences: micronaut-core, baseline build (Gradle 9.9.2) vs Provider API branch build

| | Baseline build | Provider API branch build |
|---|---|---|
| Code | baseline commit `c4fcf5622` ("chore: Bump version to 5.1.3-SNAPSHOT") | migration branch tip `f48ed2d53` (`gradle-10-migration/20260619-1844-g951-to-PAPI-20260609`) |
| Gradle | `9.9.2` (release) | `9.9.0-20261124151743+0000` (built from the Provider API migration branch, revision `8779a723`) |
| JVM | Temurin 25.0.3 | Temurin 25.0.3 |
| Tasks in graph | 741 (root), 9 (`buildSrc`) | 741 (root), 9 (`buildSrc`) |
| Build result | passed | passed |

Both builds ran `clean assemble --no-scan --no-build-cache --no-configuration-cache` with `task-dump.init.gradle`; the JSON dumps were then compared. No workaround was needed on either side.

**Read this first**

- Input property values are compared by **eager-API semantics**. Where a lazy property replaced an eager one, the dump reads the value through the eager accessor generated for that property (`org.gradle.internal.classpath.generated.<Type>_Adapter.access_get_<originalAccessor>`, or the `$$BridgeFor$$` class of a custom adapter). That is what code compiled against an earlier Gradle gets when it calls the old getter. In the Provider API branch build, 4610 input values across 446 tasks were read that way; the baseline build has no such accessors and is read as before. **No input value differs between the two builds.**
- The migration changed **no build logic** in this project (only the wrapper files, plus the generated notes and report). Every difference below comes from the Gradle distribution, from the project's own build, or from the comparison.
- Each side was run with its distribution's `bin/gradle` directly, not through the wrapper. Both sides' `buildSrc` ran from scratch (`clean` does not reach `buildSrc`, so stale `buildSrc` output from an earlier run was removed first).
- **No difference in a build product is attributable to the Gradle distribution.** The three class files that differ are a non-determinism of the project's annotation processing (see `GEN-ORDER`).
- 95 of the 741 root-build tasks differ (in an input value, a file, an outcome or a read error); all of them are covered by the rows below.
- `buildSrc` is covered too: the dump script writes one file per build.

## Reason mnemonics

| Mnemonic | Kind | Meaning | Basis |
|---|---|---|---|
| `GEN-ORDER` | Project non-determinism | A class generated by the Micronaut annotation processor lists two types in swapped order (two adjacent `ldc` class constants; everything else identical). | Verified with `javap` in this run: 4 changed lines per class, all of them the swapped pair. In the previous version of this report, recompiling the two modules in a fresh daemon gave identical bytes on both distributions; that was not repeated here. Within this run, the first branch build produced the swap in `micronaut-jackson-databind` only, the second in both modules. |
| `COMPILE-STATE` | Outputs | `previous-compilation-data.bin`, the Java incremental-compilation state, differs; not a build product. | Observed on the two `GEN-ORDER` modules only, whose compiled classes differ. |
| `KT-STATE` | Outputs | Kotlin incremental-compilation state (`last-build.bin`) differs; compiled classes are identical. | Observed; not verified in this project. The file records the time of the build. |
| `UPSTREAM` | Propagation | The file differs only because it is, or contains, the output of another task that already differs. | Verified: every such entry is the `jackson-databind` or `http-server-netty` jar or classes directory. |
| `QUERY-ERROR` | Tool noise | The dump script could not read a file input after the build ("resolution without an exclusive lock"). The property then appears on one side only, or only the error text differs. | Tool limitation. The error occurs on both sides (84 tasks in the baseline build, 77 in the Provider API branch build). Its exception class changed from `GradleException` to `IllegalResolutionException`, so the same failure reads as a difference. |
| `TOSTRING` | Tool noise | The value is an object without a stable string form; only its `toString()` text changed. | Tool limitation. Says nothing about the object's content; the individual `options.*` inputs of the same tasks are identical. |
| `GRADLE-LIBS` | Environment | Files of the Gradle distribution itself: embedded Kotlin (2.4.21 vs 2.4.20), the installation beacon, the generated `gradle-api` jar. Only `buildSrc` has these on a classpath. | Verified by path. |
| `VERSION-STRING` | Outputs | A generated source file embeds the Gradle version in a message. | Verified with `diff`: one line per file, "Precompiled Groovy script plugins built by Gradle …". |

## Changes from the previous version of this report

- `Delete` (all 72 `clean` tasks), input `followSymlinks`: `false` → `null`, previously tagged `VALUE-UNSET`, is gone. Read through `Delete_Adapter.access_get_isFollowSymlinks`, the Provider API branch build returns `false`, the same as the baseline build. The `VALUE-UNSET` mnemonic no longer applies to this project.
- `COMPILE-STATE` now shows on 2 tasks instead of 27, both of them modules whose compiled classes differ. The previous count included run-to-run variation of that file.
- `QUERY-ERROR` now also covers 14 tasks whose only difference is the exception class in the error text.
